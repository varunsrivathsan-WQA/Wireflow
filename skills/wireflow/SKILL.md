# Wireflow wireframe builder

Turn a plain-English brief ("wireframe a checkout flow", "mock up a SaaS pricing page") into **two matching deliverables built from the same brief**: a real Figma frame made of actual component instances, and a self-contained HTML file using the matching CSS classes. Never just one side unless the user explicitly asks for HTML-only or Figma-only.

Wireflow is a deliberately constrained, 66-primitive lo-fi wireframing kit (grayscale + one link blue, system font, one component per Figma page, one `.wf-*` class per primitive in `wireflow.css`) — the original 50 general-purpose primitives, plus a 16-primitive shadcn/ui-parity extension added later (chat bubbles, calendar, carousel, OTP input, skeleton loader, etc.). **The extension is not a separate category anywhere a user browses it** — every one of those 16 lives alphabetically inside its real category (see the vocabulary table below), both in Figma's page list and in the catalog. A 17th extension primitive, Kbd, was built and then removed — it never had a matching Figma page and isn't part of the shipped set; don't reintroduce it. Interactive controls and card-like surfaces use real corner radii matching shadcn/ui (see "Radius" below); pure layout/structural primitives stay flat/boxy on purpose, matching real shadcn. The constraint is the entire point — treat every rule below as a hard constraint, not a suggestion, and never invent a 67th primitive on either side.

**This skill needs the Wireflow component library available to the target Figma file** (all 66 primitives, one per page, plus the Icon component set) — it builds *into* that library, it doesn't create the library from nothing. See "Providing the component library" under Step 0 for how to get it there: check whether it's already available as a published library first, and only fall back to asking the user to duplicate the reference file if it isn't.

## Step 0 — ask which Figma file, every time

Before doing anything else, **ask the user which Figma file/link to build the wireframe into** — don't assume a file used earlier in this conversation or project still applies, and don't guess from a file name. Get either a Figma URL (extract the fileKey from `/design/:fileKey/...`) or an explicit fileKey. Do not proceed to Step 1 without it.

### Providing the component library — check for a published library before asking the user to duplicate anything

Once you have the target fileKey, check whether the Wireflow library is actually available to it before assuming the user needs to hand-duplicate a file:

1. **Call `get_libraries(fileKey)`** on the target file. This returns `libraries_added_to_file` (already subscribed, ready to use right now) and `libraries_available_to_add` (published in the org/team, but not yet added to this specific file).
2. **Look for a Wireflow match in both lists**, matching on name loosely (e.g. "Wireflow-UI-Kit", "Wireflow", or similar — a team may have renamed it slightly on publish, so don't require an exact string match).
3. **If it's in `libraries_added_to_file`:** the library is ready. Pull primitives in via `search_design_system` (scoped to that library's key via `includeLibraryKeys`) and `figma.importComponentByKeyAsync()` as each one is needed in Step 4, instead of assuming a local copy already exists on the target file's own pages. This is the best case — zero manual steps, and every wireframe uses the exact same canonical components everyone else does.
4. **If it's in `libraries_available_to_add` but not yet added:** tell the user it's available and ask them to add it to the file via Figma's Assets panel (a published library can't be subscribed to a file via the Plugin API — that step needs the user). Once they confirm it's added, proceed as in case 3.
5. **If no match appears in either list:** the library isn't published yet. Fall back to the reference file directly — tell the user the Wireflow design system isn't available as a library yet, give them the canonical reference file (`https://www.figma.com/design/Vnd1lVvmWGs19CXMtqUMqx/Wireflow-UI-Kit`), and ask them to duplicate or save a copy of it before continuing (Figma → File → Duplicate). Build into that duplicated copy's fileKey from here on, exactly as this skill has always done. Mention in passing that publishing the reference file as a team/org library (one-time action, in Figma's Assets panel) would let future builds skip this step entirely — but don't block on it or push the user to do it now.

Do this check every time, even if a previous build in this conversation already resolved it for a different file — library availability is per-file/per-team, not something to assume carries over.

Also locate `wireflow-tokens.css` and `wireflow.css`. This skill ships its own canonical copies at `references/wireflow-tokens.css` and `references/wireflow.css` (relative to this SKILL.md) — use those by default. If the current project/repo already has its own copies (for example, a team's customized fork with local changes), prefer those instead so you build against whatever the user is actually maintaining, and flag it to the user if the two versions disagree in a way that matters (a renamed or missing token, a changed primitive). Don't reconstruct the CSS from memory in either case — the vocabulary table below is for mapping a brief to the right primitive, not a substitute for the real, current file.

**Never link to these files by relative filename in the delivered HTML (`<link rel="stylesheet" href="wireflow.css">` and similar).** A linked file only works if it stays sitting next to the HTML on whatever disk opens it, and it silently breaks — raw unstyled markup, no error — the moment the HTML is sent, moved, or opened alone (exactly what happens when a chat delivers the HTML and its CSS as separate attachments). Every delivered HTML file must be genuinely self-contained: read both CSS files' actual content and inline it directly inside a single `<style>` block in `<head>` (tokens file's content first, then the primitive stylesheet's, in that order, byte-for-byte — never paraphrased or reconstructed from memory). See Step 5 for the full rule.

## Step 1 — parity check both sources before building anything

This is not optional and not a one-time setup step — run it fresh every time this skill is invoked, because either side may have drifted since the last build:

1. **Figma side:** using `use_figma` (load the `figma-use` skill first — mandatory, see Step 4), check depends on which path Step 0 resolved:
   - **Local-pages mode** (no published library, building into a duplicated reference file): list the pages in the given file and confirm there's one page per expected primitive (see the vocabulary below — 66 total, one continuous alphabetical sequence, no separate "Extended" block) plus the Icon component set (see "Icons" below), named to match. Note any primitive with no matching page (Kbd should have none — that's correct, not a gap), and any extra page that looks like a primitive not in the vocabulary.
   - **Library-import mode** (Wireflow available as a published library, per Step 0): instead of checking the target file's own pages, confirm via `search_design_system` (scoped to the library's key) that all 66 primitive names and the Icon component set actually resolve in that library — this is the library's own parity check, standing in for "does the target file have all 66 pages." A primitive the library doesn't have is the same kind of gap as a missing page in local-pages mode; treat it the same way in rule 3 below.
2. **Code side:** read `wireflow.css` and extract the actual `.wf-*` class list (grep for top-level primitive rules, not internal `__` sub-parts). Compare against the vocabulary below. Note that `wireflow.css` still groups the 16 extension primitives together near the end of the file purely to keep its own diff/history readable — that's a stylesheet-organization convenience, not a category boundary; each rule's doc comment names which of the 8 real categories it belongs to.
3. **Cross-check:** the Figma page list and the CSS class list should describe the *same* 66 primitives. If they don't agree with each other or with the table below — a primitive renamed, added, or missing on one side — **stop and flag the specific discrepancy to the user** before building, rather than silently building from whichever side looks more complete or guessing which one is "current." This mirrors how this project already handles component drift: flag it, ask, never auto-resolve.
4. **Structural quality, not just content parity:** a Figma primitive can match the CSS in content (right colors, right text, right children) while still being built wrong structurally — a plain static frame with manually-positioned children where the CSS uses `display:flex`/`grid`, or a set of separately-duplicated components standing in for what should be one component with variant properties. See "Figma structural quality" under Step 4 for what correct looks like and how to check for it; don't treat "looks right in a screenshot" as sufficient on its own for a primitive with internal layout or more than one state/size.

Only once both sides check out (or the user has confirmed how to proceed despite a flagged gap) move on.

## Step 2 — parse the brief into sections

Break the requested page/flow into the regions it implies (e.g. "pricing page" → nav, hero/intro, pricing cards, FAQ, footer). For a multi-screen flow, plan one HTML file and one Figma frame per screen unless the user asks for a single long scrolling page.

### Multi-screen flows are a click-through prototype, not a pile of disconnected files

When a brief implies more than one screen (a flow, not a single page — "wireframe the checkout flow," "mock up onboarding"), the screens must actually link to each other, not just share a design system. This applies to the HTML side only — no JavaScript, ever (see Step 6 rule 11); it's real anchor-tag navigation between real files, nothing more:

1. **Name every screen's file predictably before writing any of them**, kebab-case, so links between them are known upfront rather than guessed after the fact — e.g. a checkout flow becomes `checkout-cart.html`, `checkout-shipping.html`, `checkout-payment.html`, `checkout-confirmation.html`. Tell the user this naming convention if it's not obvious from the brief.
2. **Give every element that represents real flow navigation a real `href`** pointing at the sibling file it goes to — not `href="#"`. This includes: a primary/secondary Button that advances or backs up the flow ("Continue to payment," "Back to cart"), a Breadcrumb step, a Nav/menu item or Sidebar item where each item is genuinely a different screen (not a same-page section), a Tab bar where each tab is a distinct screen, Pagination between distinct list/detail screens, and a Link-styled button used the same way. Leave `href="#"` (or no href at all) for anything that isn't real navigation between the flow's own screens — decorative footer icons, external links the brief doesn't specify a destination for, and same-page anchors.
3. **Mark which screen is current** using the mechanisms these primitives already support — `data-active="true"` on the matching Nav/menu item, Sidebar item, or Tab bar tab; `data-current="true"` on the matching Breadcrumb step — set correctly and differently on each file, so a person clicking through actually sees where they are. This isn't optional polish; a click-through flow with no "you are here" indication isn't actually functioning as a prototype.
4. **Every file stays fully self-contained per Step 0/5 regardless** — inlined CSS, no relative `<link href>` to a stylesheet. Cross-linking between the flow's own HTML files via `href="checkout-payment.html"` is fine and expected (these files are always delivered and kept together as a set specifically so the links work); it's only the CSS files that must never be referenced this way, because those get separated from the HTML in a way the flow's own sibling screens are not meant to be.
5. **On the Figma side**, mirror the same flow with native Figma prototyping connections between frames (not JavaScript — Figma's own click-interaction/prototype feature) so the Figma side is click-through too, not just a set of disconnected static frames. Don't guess the exact Plugin API surface for this from memory — grep the `figma-use` skill's `references/plugin-api-standalone.d.ts` for "reaction" / "prototype" at build time to confirm the current method names and shapes before scripting it, the same way this skill already insists on for every other API detail.

A single standalone page (not a flow) doesn't need any of this — this section only applies once a brief implies more than one connected screen.

### Build complete pages, not sparse ones

A terse brief describes the page's *purpose*, not its full content — "wireframe a product page" is a request for a real, complete product page, not a title and one placeholder image. Before mapping elements (Step 3), check the brief's page type against the checklists below and include every section a real page of that type would have, unless the user explicitly scoped it down ("just the header" / "no reviews section"). Silently shipping a thinner page than what was asked for is exactly the kind of under-building this rule exists to prevent — when genuinely unsure whether a section belongs, ask, but default to the complete version.

These are the common archetypes and their expected sections (each section maps to primitives via the vocabulary table in Step 3 as usual — this list is about *what belongs on the page*, not which primitive builds it):

- **Product info / PDP:** breadcrumb; image gallery (Aspect ratio box + Carousel, or a grid of Image placeholders); product title (Heading) and price (Heading/Body); the Rating pattern (see "Rating" below) with a review count; variant selectors if the brief implies options (Select, Toggle group, or Radio for size/color); quantity control; primary Add-to-cart Button plus a secondary action (wishlist/Icon button); description (Body text, or Accordion item for long-form/spec content); a specs/details section (Table or a set of Accordion items); a reviews section (individual reviews as List item or Card, each pairing the Rating pattern with body text and an attribution); a related/"customers also viewed" product grid (Card); Navbar with a Search bar; Footer.
- **Marketing / landing page:** Navbar with nav items and a primary CTA Button; hero (Heading + Body + primary/secondary Button pair, often with an Image/Video placeholder); a logo/social-proof strip (Logo placeholder row); a features/benefits section (Card or icon+text rows, typically 3+ repeated); a testimonial/quote section (Blockquote or Card); pricing if implied (Card per tier); an FAQ (Accordion item, several); a closing CTA band; Footer.
- **Checkout / cart:** Breadcrumb or step indicator (Tab bar or Progress bar); line items (List item or Table, each with an Image placeholder, title, price, quantity); an order summary block (Stat/metric block or a plain Stack of Body text rows: subtotal, shipping, tax, total); form fields for address/payment (Form group, Text input, Select); primary Button to confirm; secondary Link-styled button or Breadcrumb back to cart.
- **Dashboard / analytics:** Sidebar or Navbar for wayfinding; a Stat/metric block row (several, for top-line numbers); one or more Card-wrapped chart/graph areas (Image placeholder stands in for the chart itself — Wireflow has no chart primitive, see Step 3's "no matching primitive" rule); a Table for a detail/records view; filters (Select, Search bar, Date field) above the table.
- **Settings / account:** Sidebar or Tab bar for section navigation; grouped Form group fields per settings section; Toggle/switch rows for preferences; a Button to save changes, typically pinned or at the section's end.
- **List / index / search results:** Search bar and filter controls (Select, Toggle group) near the top; a result count (Body text or Eyebrow/label); the results themselves as a Grid of Card, or a stack of List item rows; Pagination at the end; an Empty state as the documented alternative when the brief implies "no results."
- **Auth (login/signup):** Logo placeholder; Heading; Form group fields (email, password, etc.); primary Button; a secondary Link text for the alternate flow ("Don't have an account?"); optionally a Divider with an alternate-method row.

This list isn't exhaustive — for a page type not covered here, apply the same standard: think through what a real, shipped version of that page actually contains, not just what the brief's exact words mention.

### Rating — a composed pattern, not a primitive

Ratings (a product's star score, a review's score) are common enough to need a documented, consistent build — but a 5-star rating is **not** one of the 66 primitives; it's a small composition of existing ones, so it never counts toward or against the 66-primitive constraint. Build it as: a Row containing one Icon instance of `star` (added to the Icon component set specifically for this — see "Icons" above for how a new icon variant is added; `star` follows the exact same 24×24/ink-600/stroke-only styling as every other icon) sized to `data-size` matching its context, followed by Body text for the numeric score (e.g. "4.8") and, where a count is relevant, a second Body text or Eyebrow/label for it in parentheses (e.g. "(2,341 reviews)"). Keep it to one star icon plus text, not five separate star instances with partial fills — Wireflow's icons never take a fill override (see "Icons" above), and a literal 5-star fill/half-fill display would need exactly that, so the single-icon-plus-number form is the one that stays inside every existing rule rather than requiring a new exception.

### Image gallery — a composed pattern, pick one approach per slot and never mix them

A product image gallery is another small composition, not a primitive of its own — and it's a composition with exactly one real bug to avoid: building **both** a static image and a Carousel for the same gallery slot (a real PDP build shipped with a static hero Image placeholder sitting next to a separate Carousel underneath it, doubling the same content instead of picking one). The "Product info / PDP" checklist above lists the gallery as "Aspect ratio box + Carousel, or a grid of Image placeholders" — read that as two *alternative* patterns for two different needs, never as "build all of it":

- **Multiple images to browse** (the brief says or implies "photos," "gallery," "views," or shows more than one product image) → the Carousel pattern, and only the Carousel pattern: one Carousel instance (`.wf-carousel`) as the large viewport — its own `.wf-carousel__viewport`/`.wf-carousel__slide` already provide the placeholder fill, so don't additionally wrap the Carousel in a separate Aspect ratio box or add a static Image placeholder next to it — plus a Row of small square Image placeholder instances directly beneath it acting as thumbnails (3–5 is typical; Wireflow has no dedicated thumbnail primitive, so a plain small Image placeholder in a Row is the correct, deliberate composition, not a gap to fill with something new).
- **A single static image with no browsing behavior implied** (one hero shot, an avatar-style photo, a single banner image) → Aspect ratio box wrapping one Image placeholder, and no Carousel at all.

Pick whichever of the two the brief actually calls for and build only that one — a gallery slot with both a static image and a carousel present is always the bug, never a valid "more thorough" interpretation.

### Sizing discipline — fill vs. hug, so nothing overflows its container

A build can use every correct primitive and still overflow its own container if a child's sizing mode doesn't match what its parent actually offers it. Three concrete cases have shipped as real bugs; check for all three on every Card, list, and control-group build, not just when something looks obviously wrong in a screenshot:

1. **Text exceeding its card/container's width.** On the HTML side, a plain block-level text element (`.wf-body`, `.wf-heading`, etc.) wraps to its parent's width by default — overflowing text there means something is overriding that default (a stray `white-space: nowrap`, a fixed inline-block width, a genuinely unbroken long string), not a missing CSS rule to add. On the Figma side this is the actual common cause: a text node inside an auto-layout frame (a Card's title/body, a List item's label) must have `layoutSizingHorizontal: "FILL"` (paired with `textAutoResize: "HEIGHT"` so it still grows tall, never wide) so it takes exactly its parent's available width. Never leave a text node at `"HUG"` (sizes to its own content, which reads as too narrow or too wide depending on the string) or at a stale literal pixel width left over from copying an instance built at a different size — check `textNode.layoutSizingHorizontal` explicitly on every text node inside a Card, List item, or any other fixed/constrained-width primitive; don't assume a duplicated instance inherited the right sizing.
2. **Mismatched heights across a row of cards.** `.wf-grid` is a plain flex row with no explicit `align-items`, so its CSS default (`stretch`) already makes every direct-child `.wf-card` in the same row equal-height as long as they're real siblings inside one `.wf-grid` — if this breaks in HTML, check the cards are actually siblings in one flex row and not each wrapped in their own extra div. On the Figma side this needs a setting that isn't Figma's own default: the row's auto-layout frame must have `counterAxisAlignItems: "STRETCH"` — Figma defaults to `"MIN"` (top-aligned, each child hugging its own content height independently), which is exactly what produces visibly mismatched card heights the moment the cards hold different amounts of text. Set `counterAxisAlignItems: "STRETCH"` on any HORIZONTAL auto-layout row holding a set of same-row cards, and make sure each Card instance's own `layoutSizingVertical` isn't `"FIXED"` at a hardcoded height, so it actually stretches to match its tallest sibling.
3. **Button group / Toggle group overflowing its card or frame.** `.wf-button-group` is plain `display: flex` and `.wf-toggle-group` is `display: inline-flex` — both hug their own content width, neither wraps or shrinks by default, so either one overflows visibly the moment its parent is narrower than the sum of its buttons. This is a call-site problem, not a primitive bug: size the parent holding a Button group or Toggle group to actually fit it (on the Figma side, an auto-layout parent with `counterAxisSizingMode`/`primaryAxisSizingMode: "AUTO"` around the group, so the parent hugs the group's real width, rather than squeezing the group into a fixed-width parent that's too narrow for it) — never force the group into a Card or frame narrower than its natural content width. If the option count genuinely can't fit at the container's intended width, that's a signal to reduce the options shown or wrap explicitly (`flex-wrap: wrap` in HTML at the point of use, `layoutWrap: "WRAP"` on the Figma parent) rather than letting it silently overflow the edge.

## Step 3 — map every element to a documented primitive

For each piece of UI the brief implies, pick the nearest match from the vocabulary table below — never invent a class or freehand a Figma shape for something a primitive already covers, and never invent an icon that isn't in the Icon component set (see "Icons" below). If something in the brief has **no matching primitive** (e.g. a rich data-viz chart, a drag-and-drop kanban board), stop and flag it back to the user by name instead of improvising new markup/shapes or silently dropping the requirement.

### Token naming — numeric step-of-10, same on both sides

Every scale in `wireflow-tokens.css` — font size, line height, radius, spacing (space/gap/padding-vertical/padding-horizontal) — steps by 10 (10, 20, 30…) and mirrors the Figma variable names 1:1, so a token name is copy-pasteable between the two: `--font-20` in CSS is `Size/Font Size/font-20` in Figma, same pattern for `--line-*`, `--radius-*`, `--space-*` / `--gap-*` / `--padding-*-*`. Two deliberate exceptions to know about, both documented inline in `wireflow-tokens.css`:

- **Radius is numbered by pixel value, not by declaration order.** `--radius-10` = flat/0px, `--radius-20` = soft/2px, `--radius-30` = control/6px, `--radius-40` = md/10px — monotonic with size, which is why "control" (30) sits after "soft" (20) even though the underlying raw token order is flat/soft/control/md. Always use the *numbered* name (`--radius-30`) in a primitive's CSS rule and bind the matching numbered variable in Figma — never the descriptive raw name (`--radius-control`) directly.
- **Opacity's numeric value differs between the two platforms on purpose.** CSS's native `opacity` property takes 0–1, so `--opacity-50` is `0.5` in `wireflow-tokens.css`; Figma internally divides a bound opacity value by 100, so the *same* variable reads as `50` inside the Figma properties panel. This is a real, necessary platform difference — don't "fix" one side to match the other's raw number.

### Structural surfaces never tint differently from the page — only placeholder shapes do

A real lo-fi wireframe never gives a layout/region primitive (Page/Frame, Container, Section, Navbar, Sidebar, Footer) its own background tint distinct from the page it sits on — Section previously shipped bound to `--ink-50` and Footer to a flat `--ink-50` fill with no separating border, both now corrected to `--ink-0` (the same white as the page), matching Container/Card/Navbar/Sidebar. Where a structural region needs visual separation from what's next to it, that separation is a **border/divider line**, never a fill difference — see Navbar's `border-bottom`, Sidebar's `border-right`, Footer's `border-top`, all `--ink-200`. The only things that ever get a different, visibly-tinted fill are the deliberate **placeholder shapes** that stand in for real content the wireframe can't render yet: Image placeholder, Video placeholder, Avatar, Logo placeholder, Carousel's slide viewport (all `--ink-50`, several with a dashed border specifically marking them as placeholders) — plus a handful of genuinely distinct floating/chip objects that are meant to visually pop off the page rather than blend into it: Badge/tag (`--ink-100`), Toast/snackbar and Tooltip's simple bubble (`--ink-900`, inverted). When adding or auditing any primitive, ask which bucket it's in — a layout/structural region (`--ink-0` + border only) or a placeholder/floating-object shape (a real fill is correct) — never split the difference with a "just a little tint" on a structural region; that's exactly the bug that shipped and got caught.

### Color infrastructure — error/warning/success exist but are unused on purpose

`--error`, `--warning`, and `--success` (Layer 3, all three theme blocks) are real, correctly-themed tokens sitting in both the CSS and the Figma variable collection, but **no primitive references them today** — urgency in Wireflow is always communicated via a label or icon choice (e.g. Alert/banner's title text saying "Error"), never via color, per the grayscale-plus-one-blue constraint (see Step 6 rule 4). Don't wire these into a primitive's default styling just because they exist; they're there so a future explicitly-requested "make this alert red" kind of ask has a real token to reach for, deliberately conflicting with the grayscale rule until a user asks for exactly that.

### Icons

Every icon in Wireflow is a real inlined Lucide SVG (ISC license) — never an abstract box, never an icon font, never a build-time sprite step. On the HTML side every icon carries `class="wf-icon"` with `fill="none" stroke="currentColor" stroke-linecap="round" stroke-linejoin="round"`; color always comes from the parent's CSS `color`, never a separate fill/stroke override. Default size is 16px; add `data-size="md"` for 20px or `data-size="lg"` for 24px. On the Figma side, every icon is an instance of Wireflow's **Icon** component set (one variant per icon name, e.g. "chevron-down", "close", "search", "plus", "info", "globe", "mail", "message-circle", "star" — the last used specifically for the Rating pattern below, never with a fill override).

Two ways an icon appears, and they're built differently:
- **Fixed-meaning glyph** (a chevron on Collapsible, a close × on Modal/Toast, a search glyph on Search bar, calendar/nav-arrow glyphs on Calendar/Carousel/Pagination, a chevron-right separator on Breadcrumb, a globe/mail/message-circle row on Footer, etc.) — just a plain Icon instance of the right variant, same on every instance of that primitive. No swap control needed.
- **"Any icon goes here" slot** — **Accordion**'s header chevron, **Icon button**, **Icon placeholder**, **Select**'s dropdown chevron, and **List item**'s leading icon — these expose an explicit `INSTANCE_SWAP` component property named `"Icon"` on the root component (`root.addComponentProperty("Icon", "INSTANCE_SWAP", defaultComponentId)`), so a consumer can swap the icon per-instance from a dropdown in Figma's properties panel, the same way a variant property works. There is no remaining abstract-box exception — every primitive that used to hold a placeholder box (List item included) now holds a real default icon.

If you need an icon that isn't already in the library, don't fall back to an abstract shape: build a new Icon variant in the same style instead (24×24 viewBox, `stroke="#616161"` bound to the ink-600 variable, `stroke-width: 1.5`, round caps/joins, `fill="none"`) via `figma.createNodeFromSvg(svgString)`, restyle every descendant to match, wrap it in `figma.createComponent()` named `icon=<name>`, and append it to the Icon component set at the next open grid slot — then use it like any other icon instance. Flag the addition to the user rather than silently reusing an unrelated existing glyph.

**Gotcha — resizing an icon instance:** `instance.resize(w, h)` only changes the frame's declared width/height; it does **not** rescale children whose constraints aren't set to "Scale," so shrinking/growing an icon instance with `.resize()` alone leaves the internal vector paths at their original size, causing clipping or a tiny icon in an oversized frame. Always do it in this order instead: `inst.resize(24, 24)` first (restores the frame to the icon's native 24×24, matching its un-moved children), then `inst.rescale(target / 24)` (scales frame **and** every descendant vector/stroke together, anchored top-left), then re-set `inst.x`/`inst.y` if an auto-layout parent shifted it mid-script. This is the only correct way to land an icon instance at a non-native size (e.g. 16×16 inside a `data-size` default slot, or 14–20px inside a primitive like Breadcrumb's separator/Map marker/Spinner/Video placeholder). If an icon has *already* been resized incorrectly (e.g. by a prior plain `.resize()` call) and you need to correct it, don't compound the mistake by resizing again then rescaling — instead compute `factor = desiredSize / currentReportedSize` from whatever its current (wrong) size actually is, and call `rescale(factor)` alone, with no accompanying `resize()` call.

**Gotcha — binding a radius (or any) variable by ID:** `figma.variables.getVariableByIdAsync(id)` requires the **full** id string including the `VariableID:` prefix (e.g. `"VariableID:228:14"`). Passing just the bare numeric part (`"228:14"`) returns `null` silently, and a `setBoundVariable` call built from that `null` does nothing — no thrown error, no binding applied. Always re-read `node.boundVariables` after the call to confirm the binding actually landed; a lack of a thrown error is not confirmation. If you don't already have the right ID, look it up by name (`figma.variables.getLocalVariableCollectionsAsync()` → find the "Wireflow Tokens" collection → resolve each `variableId` and filter by `.name`) rather than guessing or reusing an ID remembered from a previous file — variable IDs are per-file and don't carry over.

### Radius

Four radius tokens, used by category — never a literal value on either side. Names are numbered by pixel value, not declaration order (see "Token naming" above):

- **`--radius-10` (flat, 0px):** pure layout/structural primitives — Navbar, Sidebar, Page/Frame, Footer, Table, Spacer, Image placeholder, Icon placeholder's outer dashed box. Real shadcn doesn't round these either.
- **`--radius-20` (soft, 2px):** the smallest controls — Checkbox, Tooltip's simple bubble.
- **`--radius-40` (md, 10px):** card-like surfaces — Accordion, Alert/banner, Card, Modal/dialog shell, Toast/snackbar, Logo placeholder, Tooltip's rich variant, and most of the Media/Forms/Data/Feedback extension primitives (Chat bubble, Calendar, Carousel, Collapsible section, OTP slot, and similar).
- **`--radius-30` (control, 6px):** interactive controls — Button, Badge/tag, Text input, Textarea, Select, Search bar, Icon button, Dropdown/submenu, Pagination's page-number chips, Nav/menu item's active-state highlight (this one cascades: Nav/menu item is reused inside Navbar, Sidebar, and Dropdown/submenu, so fixing it there fixes all three).

Documented literal exceptions (never tokens, but always called out in a comment on both sides): **circular** shapes use `border-radius: 50%` or an explicit `max(width, height)` (Avatar, Map marker, Skeleton's circle variant); **pill** shapes use a literal `9999px` or half-height value (Progress bar + its fill, Toggle/switch's track + knob, Slider's track + thumb); **Button group**'s segmented-control join (first child keeps its left `--radius-30` corners and squares its right corners, last child the mirror, middle children fully squared, 0 gap, and the interior borders thinned by one side to avoid a doubled seam — mirrors shadcn's `-ml-px` overlap trick).

### Layout minimums — page-edge padding is responsive, everything else isn't

The system has exactly one responsive breakpoint, and it exists specifically for page-edge spacing. **Three primitives share it identically: Container, Navbar, and Footer** — all three use `--padding-horizontal-80` (64px) above `--breakpoint-mobile` (767px, defined in `wireflow-tokens.css`) and drop to `--padding-horizontal-40` (16px) at or below it, via a real `@media (max-width: 767px)` rule in `wireflow.css` (a literal px value there, not a `var()` — `@media` conditions can't reference custom properties; it mirrors the `--breakpoint-mobile` token). These three are the only things that sit flush against the actual page/frame edge — Container as the general-purpose centered column, Navbar and Footer as the full-width top/bottom bands — so all three must always carry the identical horizontal gutter; there's no reason for one to sit closer to the edge than another on the same page. If this value ever changes, change it in all three places together, not just Container. This does not change how Container behaves when nested somewhere that isn't a page edge (inside a Card, a Modal, etc.) — there's still exactly one Container primitive; the media query is what adapts its one job, not a second variant of it.

**A real bug that shipped from exactly this kind of drift, worth guarding against on any future token change:** Container's own Figma master component was left bound to the old `--padding-horizontal-60` (32px) variable well after its CSS rule had already been updated to the responsive 64px/16px pair — the CSS-side fix landed, but nobody re-checked the Figma master component's own variable binding, so the two silently disagreed until it was caught during a later Navbar/Footer padding pass. **Whenever a padding/spacing/radius token binding changes in `wireflow.css`, treat updating the matching Figma master component's binding as its own required step, never something you assume followed automatically from the CSS edit** — check the actual bound variable on the live component (`node.boundVariables`) rather than trusting that a CSS-side fix already covered it.

Section's own vertical padding is deliberately lighter than a Card's — `--padding-vertical-50` (24px), not `--padding-vertical-70` (48px) — because Section is a page-level rhythm band meant to stack several regions, not a single boxed surface; see the doc comment on `.wf-section` in `wireflow.css` for the full rationale, and don't reach for the heavier 48px value here even though it's a valid token elsewhere.

Nothing else in the system is responsive — every other primitive's spacing, sizing, and layout is a single fixed value regardless of viewport width, same as before. Don't improvise additional breakpoints or make another primitive's padding conditional; if a brief specifically needs more responsive behavior than this, flag it rather than inventing a mechanism the system doesn't have.

Figma has no live breakpoint the way CSS does — a Figma frame is a fixed canvas — so a build that needs both a desktop and a mobile view needs two separate frames, one at `--viewport-desktop` (1440px) and one at `--viewport-mobile` (375px), each with Container's, Navbar's, and Footer's side-padding variables all bound to the matching token for that width (`padding-horizontal-80` at 1440px, `padding-horizontal-40` at 375px). The single HTML file, by contrast, can and should be genuinely responsive via the real media query — resizing the browser window should show the padding actually change at the 767px breakpoint, not just look right at whichever width it happened to be authored at.

## Step 4 — build the Figma frame

Load the `figma-use` skill (or read the `skill://figma/figma-use/SKILL.md` MCP resource) before any `use_figma` call — mandatory, not optional.

1. In the given fileKey, create one new frame per screen, named clearly (e.g. "Wireframe — Checkout: Payment step").
2. Build the frame's layout using real instances of Wireflow's own layout primitives — Page/Frame, Section, Container, Stack, Row — as VERTICAL/HORIZONTAL auto-layout frames, exactly mirroring the HTML structure being built in Step 5. Don't hand-draw layout with arbitrary rectangles; the layout is primitives too.
3. For every other element, get its component the way Step 0/1 resolved:
   - **Local-pages mode:** find its main component by locating the page whose name matches the primitive (e.g. a page named "Button") — pages are one continuous alphabetical list, not grouped by category or by original/extension — get its component/component set, and `createInstance()`.
   - **Library-import mode:** find the component via `search_design_system` (scoped to the Wireflow library's key), take its component key from the result, and pull it into the target file with `await figma.importComponentByKeyAsync(key)` before calling `.createInstance()` on the imported component — never assume the component already exists locally just because a previous call in this session imported a different primitive.
   For any icon (see "Icons" above), instantiate from the Icon component set the same way (either mode). Never draw a freehand vector, and never hardcode component ids/keys from a previous build — the file (or the library's internal keys) may differ from what was used last time.
4. Apply the brief's specific content via `instance.setProperties({...})` for variant/content component properties (introspect `instance.componentProperties` to find the right key, e.g. one starting with "Content" or "Label") — `figma.loadFontAsync(...)` for every font/style involved BEFORE setting any text.
5. Append children into their parent auto-layout frames (never set manual x/y unless deliberately overlapping two layers, e.g. Avatar-style, or building one of the documented absolute-positioning exceptions in "Auto-layout" below). Remember: for a VERTICAL auto-layout frame, `primaryAxisSizingMode` governs height and `counterAxisSizingMode` governs width — backwards from naive intuition, and the single most common cause of silently truncated frames. For HORIZONTAL frames it's reversed.
6. If any icon instance needs a non-native size, use the resize-then-rescale pattern from "Icons" above — never a plain `.resize()`, which clips the icon instead of scaling it.
7. Take a screenshot of the finished frame and check it actually matches intent before reporting done.

### Figma structural quality — auto-layout and true variants are both required

Two structural rules apply to every primitive built or touched in Figma, on top of the visual/content correctness covered elsewhere in this skill. Both are about *how* a component is built, not what it looks like — a screenshot can look completely correct while either rule is silently broken, so check the underlying node properties (`layoutMode`, `componentPropertyDefinitions`), not just a rendered screenshot.

**Auto-layout, not static frames.** Any Figma frame that corresponds to a CSS container using `display: flex` or `display: grid` must be built as a real Figma auto-layout frame (`layoutMode: "HORIZONTAL"` or `"VERTICAL"`, with `layoutWrap: "WRAP"` for a wrapping grid), never a plain static frame (`layoutMode: "NONE"`) with children manually positioned by x/y. Map the CSS onto Figma properties directly: `gap` → `itemSpacing` (bind to the matching `Spacing/Gap/gap-N` variable), `padding` → `paddingTop/Bottom/Left/Right` (bind to `Spacing/Padding Vertical/…` / `Spacing/Padding Horizontal/…`), `justify-content`/`align-items` → `primaryAxisAlignItems`/`counterAxisAlignItems` (`flex-start`→`MIN`, `center`→`CENTER`, `flex-end`→`MAX`, `space-between`→`SPACE_BETWEEN`), and an explicit CSS px `width`/`height` → `primaryAxisSizingMode`/`counterAxisSizingMode: "FIXED"` vs. `width:auto`/`fit-content` → `"AUTO"` (hug) vs. `width:100%`/`flex:1` on a child → that child's `layoutSizingHorizontal`/`layoutSizingVertical: "FILL"`.

The one real exception: **don't** force auto-layout onto something the CSS itself positions with `position: absolute` or `position: relative` + absolutely-positioned children — converting these would change the actual mechanism, not just tidy up the metadata. The documented cases in this kit are: Slider's fill/thumb over its track, Toggle/switch's knob over its track, Carousel's prev/next controls over its viewport, Table's native row/cell grid, and any primitive with literally no flex/grid declared in its CSS at all (Progress bar, Spinner, Divider, Skeleton loader — these are bare leaf shapes with nothing to lay out in the first place). Leave those as plain frames; don't "fix" them into auto-layout just for the sake of it.

Every icon instance or image-placeholder child sitting inside an auto-layout frame should have its `constraints` property set to `{horizontal: "CENTER", vertical: "CENTER"}`, not left at the Figma default `{horizontal: "MIN", vertical: "MIN"}` ("top-left anchored"). Auto-layout governs the actual rendered position regardless of this setting, so a stale `MIN/MIN` constraint won't cause a visible bug today — but it's wrong metadata that misdescribes the component's intended resize behavior, and it's worth setting correctly at creation time rather than leaving it for a later cleanup pass.

**Variants, not duplicate components.** Any primitive with more than one state, size, or style meant to be browsed as options of *the same thing* — a size scale (Spacer's 8 sizes), a ratio/shape scale (Aspect ratio box's 3 ratios), an on/off or default/alternate state (Toggle/switch, Form group's error state, Nav/menu item's active state), a content-richness variant (Tooltip's simple vs. rich) — must be built as **one Figma component set with real variant properties**, never as several separately-named, separately-maintained duplicate components or instances that merely *look* related. A true variant set is what lets a consumer pick the size/state/ratio from a dropdown in Figma's properties panel the same way `data-*` attributes drive it in HTML, and it's what keeps N near-identical copies from drifting out of sync over time.

To build one: construct each state as its own plain `COMPONENT` first (getting each one visually correct independently, exactly as you would any other primitive), name each one `"<PropertyName>=<value>"` (e.g. `"Ratio=4-3"`, `"Ratio=16-9"`, `"Ratio=1-1"`, or `"State=default"`/`"State=error"`) — Figma infers the variant property and its options directly from this naming convention — then combine them with `figma.combineAsVariants([comp1, comp2, ...], parentPage)` and rename the resulting `COMPONENT_SET` to the primitive's plain name (e.g. `"Aspect ratio box"`). `combineAsVariants` auto-arranges the variants into a tidy grid inside the new set and leaves the set's own `layoutMode` as `"NONE"` — that's correct and expected; a component set's outer wrapper is a canvas arrangement, not a CSS-mapped container, so don't try to auto-layout it. Every existing multi-state primitive in the reference Wireflow library (Aspect ratio box, Spacer, Tooltip, Toggle/switch, Form group, Nav/menu item) is already built this way — use one of those as a reference if unsure what the end state should look like.

### Figma/HTML parity check — a concrete diff, not a side-by-side glance

"Looks similar in two screenshots" is not the bar — a build can look roughly right while actually using different primitives, a different section order, or fewer sections on one side than the other (this exact failure — a Figma build with real search bars, reviews, and detail sections, paired with an HTML file missing most of them — is what prompted this rule). Run this check after both Step 4 and Step 5 are built, before Step 7, and treat a mismatch as something to fix, not something to mention and move past:

1. **Extract the HTML's primitive list.** Parse the delivered HTML for every top-level `.wf-*` class in document order, one entry per element (e.g. `wf-page, wf-navbar, wf-section, wf-container, wf-card, wf-card, wf-footer`). Repeats matter — two `.wf-card` in a row is a different structure than one.
2. **Extract the Figma frame's instance list.** In the same `use_figma` call that builds or last touches the frame, walk the frame's node tree (`frame.findAllWithCriteria({types: ['INSTANCE']})`, or `frame.query('INSTANCE')`) in document order and map each instance to its `mainComponent`'s (or, for a variant instance, its parent set's) name — e.g. `Page/Frame, Navbar, Section, Container, Card, Card, Footer`. Also capture nesting depth or parent chain for each, not just a flat list — two lists with the same primitives in the wrong nesting still fail this check.
3. **Diff the two lists.** They should describe the same sequence of primitives in the same nesting — same primitive appearing the same number of times, in the same relative order and the same parent/child relationships. A primitive present on one side and missing on the other, a different count, or a different nesting level is a real parity gap, not a stylistic difference.
4. **Diff section-level content, not just structure.** For each major region (nav, hero, each content section, footer), confirm both sides show the same number of repeated items (e.g. both show 3 pricing cards, not 3 on one side and 1 on the other) and the same headings/labels — this is what catches the "Figma has a full reviews section, HTML has none" class of gap that a pure class-name diff can miss if a section is dropped on one side entirely rather than emptied.
5. **Fix, don't just report.** If step 3 or 4 surfaces a gap, add the missing primitive/section to whichever side is behind before calling the build done — this check runs *before* Step 7's report, not as a substitute for building it right the first time. Only surface a mismatch to the user (per Step 6 rule 10) if fixing it would require a decision only they can make (e.g. the brief itself was ambiguous about whether a section belongs).

## Step 5 — build the matching HTML file

- One **self-contained** HTML file per screen. Never `<link rel="stylesheet" href="...">` to `wireflow-tokens.css` or `wireflow.css` — per Step 0, read both files' actual current content and inline them, byte-for-byte, inside a single `<style>` block in `<head>` (tokens file first, then the primitive stylesheet, in that order). The delivered file must render correctly opened completely alone, with no sibling file present — that's the test, not just "does it render on my machine right now."
- Structure it with the exact same layout nesting (Page → Section → Container → Stack/Row → primitives) used for the Figma frame in Step 4 — the two should read as the same screen, not two different interpretations of the brief. See Step 4's new "Figma/HTML parity check" for how to verify this concretely rather than by eye.
- Real, plausible placeholder copy for the brief's domain (not raw "Lorem ipsum" everywhere) — the same copy used for the Figma instances' text overrides, so both sides say the same thing.
- **Genuinely responsive, not just correct at one width.** Because `wireflow.css` now ships a real `@media (max-width: 767px)` rule (see "Layout minimums" above), the delivered HTML must actually exercise it — Container's page-edge padding should visibly change if the browser window is resized across 767px. Don't hardcode a single viewport's worth of markup and call it done; nothing about the HTML output should assume a fixed browser width.

## Step 6 — hard rules while composing (both sides)

1. **No invented classes, freehand shapes, or invented icons.** If it isn't in the table above, it isn't a Wireflow primitive; if it isn't in the Icon component set (Figma) / a real inlined Lucide SVG (HTML), it isn't a Wireflow icon (see "Icons" above for how to add a genuinely missing icon the right way, instead of faking one).
2. **Variants only via documented mechanisms** — CSS `data-` attributes (`data-variant`, `data-level`, `data-active`, `data-current`, `data-checked`, `data-size`, `data-role`, `data-shape`, `data-direction`, `data-ratio`, `data-selected`, `data-muted`, `data-position`, `data-sortable`) on the HTML side, real component variant properties built as a component set (and, for Accordion's chevron / Icon button / Icon placeholder / Select's chevron / List item's icon, the `"Icon"` instance-swap property) on the Figma side — see "Variants" under Step 4 for how a variant set is built correctly. Never a modifier class, a one-off manual style override, or a separately-duplicated component for something a variant already covers or should cover.
3. **Nothing outside the token file, on either side** — including radius. No literal hex colors, no arbitrary pixel spacing/radius/font-size in the HTML except the documented circular/pill/structural-join exceptions called out in "Radius" above; every Figma property bound to the Wireflow Tokens variable collection, never a literal value typed into the properties panel (same exceptions apply, and only those; remember the `VariableID:` prefix gotcha above when binding one programmatically). If a value isn't a token in `wireflow-tokens.css` and isn't one of the documented exceptions, it doesn't belong in either output.
4. **Grayscale + one blue, and urgency is a label/icon, not a color** — on both sides (see "Color infrastructure" above for why the error/warning/success tokens exist but stay unused).
5. **Structural surfaces never carry their own tint** — Page/Frame, Container, Section, Navbar, Sidebar, Footer are always `--ink-0` (same as the page), separated from neighbors by a border/divider, never a fill difference. A visible fill is reserved for placeholder shapes and floating/chip objects only — see "Structural surfaces never tint differently from the page" above for the full list of which bucket each primitive is in. Don't add a "subtle" background tint to a layout primitive to make regions easier to tell apart — that's the exact bug this rule exists to prevent.
6. **Page-edge padding is responsive; build the HTML so it actually is** — 64px above 767px, 16px at or below it, via the real `@media` rule (see "Layout minimums" above), and the delivered HTML must be resizable across that breakpoint, not authored for one fixed width.
7. **Build the complete page, not a sparse one** — check the brief's page archetype against the content checklists under "Build complete pages, not sparse ones" (Step 2) and include every section a real page of that type has, unless the user explicitly scoped it down.
8. **Every delivered HTML file is genuinely self-contained for its CSS** — both CSS files' content inlined into one `<style>` block, no relative `<link rel="stylesheet" href="...">` to either CSS file, ever (see Step 0 and Step 5). This doesn't prohibit a `<a href="other-screen.html">` between a flow's own sibling screens — see rule 11 — only stylesheet links are banned.
9. **Figma and HTML must match structurally, not just look similar** — run the Figma/HTML parity check under Step 4 before reporting done; a build that passes a glance but has different nesting, different primitives, or missing sections on one side is not done.
10. **Flag, don't guess**, on anything with no matching primitive or icon, on a source-parity gap found in Step 1, or on any mismatch discovered between the two finished outputs — always ask rather than silently improvising or letting one side lead without telling the user.
11. **Multi-screen flows are real click-through, and never via JavaScript** — every element that represents flow navigation gets a real `href` to the sibling screen it goes to, the current screen is marked via the existing `data-active`/`data-current` mechanisms, and Figma gets matching native prototype connections between frames. No `<script>` tag, inline event handler, or any JavaScript anywhere in the deliverable — that boundary doesn't move even for this. See "Multi-screen flows are a click-through prototype, not a pile of disconnected files" under Step 2 for the full rule.
12. **Text, rows, and control groups must fill or hug correctly, never overflow** — text nodes inside a fixed-width primitive get `layoutSizingHorizontal: "FILL"` (never left at `"HUG"` or a stale fixed width), a row of same-row cards gets `counterAxisAlignItems: "STRETCH"` so they render equal-height, and a Button group/Toggle group's parent is sized to actually fit it (or wraps explicitly) rather than letting the group blow past its container's edge. See "Sizing discipline" under Step 2 for all three cases in full.
13. **Image gallery is one composed pattern per slot, never both at once** — a gallery with multiple images to browse is Carousel-plus-thumbnails; a single static image is Aspect ratio box plus one Image placeholder; never build both a static image and a Carousel for the same gallery slot. See "Image gallery" under Step 2 for the full rule.

## Step 7 — report back

Deliver the HTML file(s) (e.g. via SendUserFile) and the Figma frame's URL (`https://figma.com/design/<fileKey>/...?node-id=<id>`), state which primitives (and which icons) were used for anything non-obvious, and surface: any Step 1 parity gaps, anything flagged in Step 3 with no matching primitive, the outcome of the Step 4 Figma/HTML parity check (confirm it was run and passed, don't just omit it), and any difference between the two finished outputs that a straight re-read of both doesn't fully explain. For a multi-screen flow, also confirm the click-through links actually work (which screen each navigation element goes to) and that the Figma prototype connections mirror them — don't just mention the screens were built, confirm they're actually linked.
